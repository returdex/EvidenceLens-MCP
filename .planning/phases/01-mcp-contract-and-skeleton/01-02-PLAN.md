<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| MCP client -> Zod schema | Untrusted JSON must be validated before handler logic. |
| Request reference strings -> future filesystem layer | Opaque references may later become path inputs and must not normalize unsafe characters silently. |
| Error helper -> MCP client | Validation failures cross back to the client and must not leak internals or secrets. |
| Contract tests -> implementation | Tests must catch accidental expansion of capabilities beyond read-only review. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-06 | Tampering | `reviewRequestSchema` evidence references | mitigate | Reject null bytes and control characters; document references as opaque metadata until Phase 3 allowlist enforcement. |
| T-01-07 | Denial of Service | Objective/evidence payloads | mitigate | Enforce 4000-character objective limit and 20-item evidence limit; test limit failures. |
| T-01-08 | Elevation of Privilege | Tool registry | mitigate | Contract test asserts only read-only `review_evidence` capability is exposed; no write/delete/mutate tools. |
| T-01-09 | Information Disclosure | Error serialization | mitigate | `toToolErrorResult()` sanitizes messages and returns stable codes without stack traces, env vars, raw filesystem paths, or provider details. |
| T-01-10 | Malformed Request Handling | Tool handler | mitigate | Parse all input through Zod before response creation and return `INVALID_REQUEST`/`LIMIT_EXCEEDED` JSON for rejected requests. |
| T-01-11 | Repudiation | Successful response metadata | mitigate | Include `requestId`, server name/version, and ISO `generatedAt` in schema-valid responses for later audit linkage. |
</threat_model>
