### 新发现：rubric 版本差异

`S-RUBRIC-LOCAL` 是四档，C.1–C.3 最高档含 secure / well-designed / robust 等质量要求，但没有后来截图的完整 industry standards 尾句。`S-FEEDBACK` 的评分表有五个数值档，另区分 1.15 的 some best practices 与 1.25 的 reasonable best practices and industry standards。

因此不能说最初提示词确定「删掉了它当时拿到的 industry standards 原文」。它仍过度依赖功能检查，但也可能使用了不同版本的标准。新版何时发布、提交前是否可访问，当前未知。应登记来源时间与版本差异，保留旧标准中的质量要求，并在重要审查前确认当前评分表；不能用事后版本重写事前证据。

## 建议调整：优先级与验收条件

### P0：在 Phase 21 规划中明确报告完整性

- 交接摘要给出关键行动，同时提供完整发现账本。每个产生的发现有稳定 ID、依据、关联 criterion、状态与处置。无需把全部细节重复塞进主对话。
- Low 可以保留 Low；用户暂不处理记录 deferred，不能变成 resolved。删除、降级、合并必须有依据，合并保留原 ID 映射。失败或截断不能伪装为空发现。
- 分开输出「功能证据」「最高档支持/反证」「提交准备状态」「覆盖未知」。全部构建通过不能自动生成 HD-ready。
- 初次审查先给发现账本，再生成摘要并核对 ID 完整性。结构化核对能够发现已记录项丢失，但不能保证模型内部从未漏想；后者靠反例任务与语义评估。

### P0：另立审查质量工作包，避免静默扩大已批准阶段

- 每个 criterion 保留原档位的质量限定语、支持证据、阻止最高档的证据（可写未找到并标覆盖）、不确定性与改进建议。没有来源时不发明分数区间。
- 针对实际功能关系构造负例：创建者→评分者；角色→导航和直接访问；管理员→真实操作及展示证据；源码凭据→报告安全声明。只列组件不足以覆盖业务行为。
- 为要求与版本建立适用范围：允许纯前端、要求安全体验、教师推荐 Firebase 可以同时成立；分别记录，不使用简单来源排序把冲突抹掉。
- 独立审查首轮只读官方材料和指定提交候选；上一轮结论/自评作为待核对象，后置比对。对必要的作者自评仍需读取，但不能当判分证据。
- 在设计阶段和关键实现后执行档位审查；提交前 5–7 天是调度建议而非课程要求。临近截止只影响修复顺序，不改变风险本身。

### P1：真实案例评估及反馈回灌

- 使用下述案例做提交前盲测、加入既有结论的对照、评分反馈对账、受控修改后的复查和早期规划测试。
- 评估发现保留率、无依据的最高档背书、错误新增要求、反证遗漏及错误关闭；不训练成看到 A1.3 就输出 70。
- 模型输出、实际 prompt hash、输入版本和人工评判保留；评审者分歧需要裁决。不能只以关键词出现或 JSON 通过宣称审查质量改善。
- 本案例长期用于回归，另保留未参与改写提示词的新案例作外部检验，避免只对已知事故有效。
